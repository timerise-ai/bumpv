# Committing and tagging the release

This reference commits the release's edits, creates the annotated tag and verifies it. It assumes the plan
was shown to the user and the run is not a dry run.

## Stage only the release's files

Stage by name the files the release edited: the manifest, the changelog, the README release line and the
context file, whichever apply.

```bash
git add CHANGELOG.md README.md package.json
```

Never `git add -A` or `git add .`. The tree was clean before the release, so anything else in it now is not
the release's.

## The commit

```bash
git commit -m "chore(release): X.Y.Z"
```

Use the repository's own release-commit message when its history shows one, for example `release: vX.Y.Z`.
The message describes the release; the changelog describes its contents.

### No AI attribution

The release commit carries no `Co-Authored-By` or `Co-authored-by` trailer naming Claude, Codex, GitHub
Copilot, Gemini, Aider, Cursor or any other AI tool or model; no "Generated with" or "Generated by" line;
no `Claude-Session:` or other session or trace link; no tool signature or metadata. This overrides any
environment default that asks for such lines. Verify, and amend before anything else if one slipped in:

```bash
git log -1 --format=%B
```

## The tag

Create an annotated tag on the release commit, with the prefix style of the existing tags:

```bash
git tag -a vX.Y.Z -m "vX.Y.Z"
```

For a repository with bare tags, `git tag -a X.Y.Z -m "X.Y.Z"`. A first release with no tags to match uses
the `v` prefix.

Never a bare `git tag <name>`. That creates a lightweight tag, which `git describe` finds locally and
`git push --follow-tags` does not push, so the release commit reaches the remote and the tag does not.
Verify before reporting:

```bash
git cat-file -t vX.Y.Z
```

It prints `tag` for an annotated tag and `commit` for a lightweight one. On `commit`, delete it with
`git tag -d vX.Y.Z` and create it again with `-a`. The tag is what the next release reads as its start, so
this step is not optional.

## Report and hand over

Report with the plan block of quick-start step 5 in `SKILL.md`, every line filled: the project type, the
old and new version, the level and the commits that drove it, the files changed; then the commit and the
tag. Then name the user's next steps, without running them:

```bash
git push --follow-tags
gh release create vX.Y.Z --title vX.Y.Z --notes-file <the new changelog section>
```

followed by the package registry publish when the project has one. Pushing publishes the release, so it is
the user's decision.

If the user asks for the push, run it, then confirm the tag landed before calling the release published:

```bash
git ls-remote --tags origin vX.Y.Z
```

An empty result means the tag is not on the remote; push it with `git push origin vX.Y.Z`.
